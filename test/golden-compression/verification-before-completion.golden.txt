# Skill: verification-before-completion

# Verification Before Completion
## Evidence contract
Every completion claim needs evidence. Evidence remains valid while its tested
content, coverage, runtime, dependencies, and relevant environment are unchanged.
A new message, commit SHA, branch, PR, or merge commit alone does not invalidate it.
Do not confuse checking evidence with executing the same validation again.
## Procedure
1. Name the claim and its actual target: file, tested tree, deployment, PR, or runtime.
2. Find the existing result and its tested inputs, suite, context, verdict, and log.
3. Reuse a valid result. If the equivalent run is active, wait on that run; do not
   launch a second one. In superpowers-plus, `tools/test-all.sh` and its CI own test receipts;
   elsewhere use the active repository's equivalent runner and policy.
4. If relevant inputs changed or proof is missing, run only the required missing
   validation through the authoritative runner. Explain the invalidation reason.
5. Read the result. A failure, cancellation, timeout, skipped check, missing receipt,
   or unverifiable producer never becomes PASS. Do not write receipts or sentinels.
6. Check loose ends within the assigned task. Resolve must-address items; disclose
   deliberately deferred issues and version/platform limitations.
7. Report the observed result and stop when the user's acceptance criteria pass.
## Reviews and sentinels
Use the repository's read-only readiness/parser tools, not an invented SHA grep.
In superpowers-plus run `tools/push-readiness.sh --json` against the actual target
range; do not assume another repository provides that helper.
Its native consumers recognize content-scoped review clearance across unchanged
merges and amends. A different HEAD SHA is not by itself a reason for another review.

- Missing or invalidated clearance: use the active repository's review routing
  (`tools/review.sh` in superpowers-plus).
- Valid clearance and unchanged reviewed scope: reuse it; do not dispatch again.
- Uncommitted relevant changes: review the actual changed snapshot before claiming
  it is covered. Ignore unrelated work only with an explicit scope boundary.
- A material finding or new relevant change requires delta review; a clean review
  does not require an arbitrary second round.
## Progress and completion are different
A progress update may report an existing command's observed status. It does not
invoke tests, review, repository-health audits, or TODO maintenance again. During
an external wait, keep one watcher and its saved log; do not reload skills or
reopen settled design decisions. A brief status update is not a new work unit.

Before waiting, distinguish required acceptance/release checks from advisory or
unrelated post-merge health checks. Never bypass a required check. Do not expand
completion into an unrequested audit, a new promotion, or a wait for unrelated
workflows. Use `holistic-repo-verification` for an explicit health audit.
## Claims and evidence
| Claim | Required evidence |
|---|---|
| Tests pass | Successful authoritative receipt/log for the relevant content and context |
| Bug fixed | Original failure path passes; required regression coverage passes |
| Artifact written | Read back the relevant output |
| PR opened/merged | Forge state for the exact PR/head; required merge checks satisfied |
| Deployed | Installed artifact matches approved source and required deployment checks pass |
| Native compatibility | Actual tested tool version/platform, not an older handoff assumption |
## Do not repeat work to manufacture freshness
- Do not rerun the full suite because another skill also asks for verification.
- Do not rerun a review because a merge changed only history or metadata.
- Do not replace a reusable receipt with a hand-written success assertion.
- Do not treat a cache hit as wider coverage than the producer actually ran.
- Do not run global task maintenance when this task has no owned task-list changes.
- Do not call a partial result complete; name the missing acceptance criterion.
## Failure cases
| Failure | Required response |
|---|---|
| Same inputs requested twice | Reuse the pass or wait for the existing owner |
| Runtime, dependencies, source, suite, or relevant environment changed | Invalidate that result and validate the new inputs once |
| Missing/forged/cancelled producer | Stop or run genuinely uncovered inputs according to runner policy; never claim PASS |
| Required check still pending | One watcher; no duplicate test invocation |
| Acceptance passed, unrelated health warning remains | Disclose it without inventing additional release gates |
